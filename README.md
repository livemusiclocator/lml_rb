# LML

[![CircleCI](https://dl.circleci.com/status-badge/img/circleci/LAffxdG5hFmx6iynRMGH5a/3NquNLfh34PueBmVqPWSwm/tree/main.svg?style=svg&circle-token=f22edd6262f0dad12f7984f1236d7dc43157ae8c)](https://dl.circleci.com/status-badge/redirect/circleci/LAffxdG5hFmx6iynRMGH5a/3NquNLfh34PueBmVqPWSwm/tree/main)

This is the rails app: the API, the admin, and the server rendered pages that host
the gig explorer.

The gig explorer itself is a separate react app in
[lml_frontend_client](https://github.com/livemusiclocator/lml_frontend_client),
served from firebase rather than from this app's asset pipeline. For how the
components fit together, and which combination of them to run for the work you are
about to do, see the
[shared lml README](https://github.com/livemusiclocator/lml/blob/main/README.md).

## Getting started

Clone and symlink the shared lml repo

```
git clone git@github.com:livemusiclocator/lml.git ..
ln -s ../lml lml
```

Install prerequisites

```
make install
```

Run postgres in docker container on the default 5432 port.

```
docker run \
    --rm \
    --name postgres-default \
    -d \
    -p 5432:5432 \
    -e POSTGRES_HOST_AUTH_METHOD=trust \
    -e PGDATA=/var/lib/postgresql/data/pgdata \
    -v postgres-default:/var/lib/postgresql/data \
    postgres
```

Launch tmux session

```
tmux -L lml_rb
```

Start caddy (in one tmux window)

```
make caddy
```

Install gems

```
bundle
```

install precommit hooks if you want to:

```
lefthook install

```

Create databases and add seed data

```
bin/rails db:reset
```

Start rails (in another tmux window - ctrl-b c)

```
bin/dev
```

Browse to https://api.lml.test/admin and log in as admin@example.com and password password


## Active admin styles

Conflicts with tailwind and sass-rails mean we had to take out sass-rails and sass in general. As a result, the active_admin.css has been prebuilt from the former scss code. To refresh these styles, something like the following will work:

+ Restore old active_admin.scss file
+ Add gem "sass-rails" to Gemfile
+ bundle install
+ rails assets:precompile
+ Find active_admin*.css in public/assets/
+ Copy contents to new app/assets/stylesheets/active_admin.css
+ Remove Sass gem and .scss file

## The gig explorer front end

`app/views/web/layouts/explorer.html.erb` renders the page that hosts the explorer.
It does not bundle any of it. Instead the helpers in
`app/helpers/web/explorer_helper.rb` emit script and link tags pointing at a
separately deployed build, and a `window.APP_CONFIG` blob (rendered by
`app/views/web/explorer/explorer_config.json.jbuilder`) that tells the front end
which API to call, which locations exist and which map pin themes to use.

Which build you get is decided by `config/spa_assets.yml`, one entry per rails
environment:

| Environment | Bundle |
| --- | --- |
| production | `assets.livemusiclocator.com.au/lml_gig_explorer_live` |
| test | `.../lml_gig_explorer_beta` |
| development | `.../lml_gig_explorer_dev` |

That file is checked in and is regenerated by `rake spa:fetch`, which reads each
build's `manifest.json` off firebase.

### Working on rails only

Nothing to do. `bin/dev` loads the `_dev` bundle from firebase - whatever was
published by the last person to deploy the front end. This is the right default
when you are changing models, the API or the admin.

Note that a front end deploy replaces that bundle, so it can change under you.

### Working against a local front end

Check out the front end as a sibling of this repo and start a watching build:

```bash
git clone git@github.com:livemusiclocator/lml_frontend_client.git ../lml_frontend_client
cd ../lml_frontend_client
make install
make watch      # rebuilds dists/firebase_root/lml_gig_explorer_dev on every change
```

Caddy serves that directory at `https://assets.lml.test`, mirroring the paths and
the CORS header firebase uses. If you set caddy up before this existed, **stop it
and run `make caddy` again** - the caddyfile is regenerated on each start.

Then point rails at it with `SPA_BASE_URL`, honoured in development only by
`config/initializers/spa_assets.rb`:

```bash
SPA_BASE_URL=https://assets.lml.test/lml_gig_explorer_dev bin/dev
```

It is read at boot, so changing it means restarting rails.

To avoid typing it every time, put it in `.env`. `bin/dev` runs foreman, which
loads that file automatically, and `/.env*` is already gitignored so it stays
per developer:

```
SPA_BASE_URL=https://assets.lml.test/lml_gig_explorer_dev
```

Comment the line out and restart to go back to the deployed bundle.

In this mode `explorer_config.json.jbuilder` points the front end at
`https://api.lml.test/gigs`, so it talks to your rails and the whole stack is
local.

To check which bundle you are actually serving:

```bash
curl -s https://www.livemusiclocator.com.test/ \
  | grep -oE '(src|href)="[^"]*lml_gig_explorer[^"]*"' | sort -u
```

Prefer `SPA_BASE_URL` over running `rake spa:fetch` locally. That task rewrites the
checked in `spa_assets.yml`, re-fetches the live and beta entries over the network
as a side effect, and cannot read a manifest from caddy's self signed certificate
anyway.

## Where everything deploys

| What | Where | How |
| --- | --- | --- |
| this app | heroku, app `live-music-locator` | `git push heroku main` (see below) |
| the gig explorer | firebase hosting, project `lml-seo` | `./deploy_firebase` in `lml_frontend_client` |

Both are manual. Tests run on CircleCI but do not gate either deploy.

Subdomain routing is split: some city editions are served by this app and some are
still served by the standalone SPA. The local mapping is in the shared repo's
`bin/makefile/caddy`, and is tabulated in the
[shared lml README](https://github.com/livemusiclocator/lml/blob/main/README.md).
